# Установка 1cmcp

Это руководство для внедренца и администратора. Продукт состоит из двух частей, которые ставятся отдельно:

| Часть | Где | Зачем |
|---|---|---|
| Слой A — расширение `мкпКоннектор` | внутри информационной базы 1С | HTTP-сервис, интроспекция, права, журнал |
| Слой B — шлюз `onecmcp` | Python-процесс или контейнер **рядом** с 1С, не в интернете вместе с базой | MCP для агентов, REST-проекция, кэш метаданных |

Прямая публикация HTTP-сервиса 1С в интернет **запрещена**. Снаружи виден только шлюз. Между шлюзом и 1С — внутренняя сеть, VPN или mTLS.

Сейчас фаза 1: чтение и интроспекция. Запись документов, отчёты СКД и произвольные запросы ещё не включены (шлюз и расширение отвечают `501`).

Два контура:

1. **Без базы 1С** — мок слоя A. Нужен, чтобы проверить шлюз, MCP и сценарии агента за минуты.
2. **С живой 1С** — расширение + публикация + шлюз. Нужен для стенда и пилота.

---

## 1. Что должно быть на машине

### Для контура с моком (разработка, демо, CI)

- Linux, macOS или Windows
- Python **3.12+**
- `git`
- опционально Docker Compose v2

### Для контура с живой 1С

Всё из списка выше, плюс:

- платформа **1С:Предприятие 8.3.20 или новее** (режим совместимости расширения — `Version8_3_20`);
- Конфигуратор с правом менять расширения;
- веб-сервер, который 1С умеет публиковать: Apache 2.4 или IIS (как принято у вас);
- клиентские лицензии: каждый сеанс HTTP-сервиса занимает лицензию (см. раздел 8);
- пользователь ИБ, от имени которого будет работать HTTP-сервис.

Расширение — дополнение (`AddOn`) **без заимствованных объектов** типовой. Его можно ставить на УТ 11, ERP 2, БП 3.0 и самописную базу с одним и тем же каталогом `extension/src`.

## 2. Получить исходники

```bash
git clone https://github.com/chastnik/1cmcp.git
cd 1cmcp
```

Рабочая ветка фазы 1 — `main` после слияния PR либо `cursor/phase1-read-introspection-e909`, пока PR открыт.

Структура, которая нужна при установке:

```
extension/src/          ← выгрузка расширения для Конфигуратора
gateway/                ← пакет Python onecmcp
specs/openapi.yaml      ← контракт HTTP API
docs/                   ← это руководство и ADR
docker-compose.yml
.env.example
docs/claude-desktop.mcp.json
```

## 3. Контур без 1С: мок + шлюз

Мок повторяет контракт слоя A: `GET /v1/health` без токена, `meta`/`data` с `Authorization: Bearer dev-token`, фикстуры `Catalog.DemoCounterparties` и `Document.DemoShipments`.

### 3.1. Python (рекомендуется для разработки)

```bash
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
python -m pip install -U pip
python -m pip install -e "gateway[dev]"
```

Проверка, что пакет виден:

```bash
python -m onecmcp --help
```

Должны быть команды `serve`, `mock1c`, `mcp`.

Скопируйте шаблон переменных (файл `.env` в git не попадает):

```bash
cp .env.example .env
```

Для мока достаточно значений из шаблона: `ONEC_BASE_URL=http://127.0.0.1:18080` и `ONEC_TOKEN=dev-token`.

Запуск **двух** процессов (два терминала):

```bash
# терминал 1 — мок слоя A
python -m onecmcp mock1c --host 127.0.0.1 --port 18080

# терминал 2 — REST-шлюз
python -m onecmcp serve --host 127.0.0.1 --port 8000
```

Проверка:

```bash
curl -sS http://127.0.0.1:8000/health
curl -sS http://127.0.0.1:8000/ready
curl -sS http://127.0.0.1:8000/v1/health
curl -sS -H "Authorization: Bearer dev-token" \
  "http://127.0.0.1:8000/v1/meta/search?q=отгрузка"
```

Ожидание: `health` и `v1/health` — `200` и `"status":"ok"`; поиск — объект `DemoShipments`. Без заголовка `Authorization` запрос к `/v1/meta` вернёт **401**.

Автотесты того же контура, что GitHub Actions:

```bash
./scripts/ci.sh
```

Порог покрытия пакета `onecmcp` — **90%**.

### 3.2. Docker Compose

Из корня репозитория:

```bash
docker compose up --build
```

Поднимаются:

| Сервис | Порт на хосте | Назначение |
|---|---|---|
| `mock1c` | 18080 | мок адаптера 1С |
| `gateway` | 8000 | REST-шлюз; ходит в мок с токеном `dev-token` |

Проверка та же: `curl http://127.0.0.1:8000/v1/health`.

Остановка: `Ctrl+C` или `docker compose down`.

## 4. Контур с живой 1С: расширение

Админ-панели в расширении ещё нет (фаза 4). Настройка клиентов, токенов и словаря делается через стандартные формы справочника и регистров сведений.

### 4.1. Загрузка из файлов (каталог `extension/src`)

1. Откройте информационную базу в **Конфигураторе**, платформа 8.3.20+.
2. Меню **Конфигурация → Расширения конфигурации**.
3. **Добавить**.
   - Имя: `мкпКоннектор`
   - Префикс: `мкп`
   - Назначение: **Дополнение** (`AddOn`)
   - Режим совместимости: **8.3.20**
   - Активно: да
   - Безопасный режим: **выключить** (HTTP-сервис и привилегии роли иначе не отработают как задумано)
4. Выделите созданное расширение. **Конфигурация → Загрузить конфигурацию из файлов…**
5. Укажите каталог `extension/src` репозитория (внутри должен лежать `Configuration.xml`).
6. Подтвердите загрузку. Если Конфигуратор предупредит о различии имени/UUID — для чистой установки согласитесь с конфигурацией из файлов.
7. **Конфигурация → Обновить конфигурацию базы данных** (для расширения). Дождитесь конца реструктуризации.

После загрузки в дереве расширения должны быть:

- роль `мкпДоступКоннектора`
- общие модули `мкпМаршрутизатор`, `мкпБезопасность`, `мкпСериализация`, `мкпИнтроспекция`, `мкпДанные`
- HTTP-сервис `мкпAPI` (корневой URL `mcp`)
- справочник `мкпКлиентыИнтеграции`
- регистры `мкпПравилаДоступа`, `мкпСемантическийСловарь`, `мкпЖурналВызовов`

Если объекта нет — загрузка прошла не из того каталога или расширение не обновлено в БД.

### 4.2. Если уже есть файл `.cfe`

1. **Конфигурация → Расширения конфигурации → Добавить из файла** (или «Загрузить расширение из файла»).
2. Выберите `.cfe`.
3. Обновите конфигурацию базы данных расширения.

Сборки `.cfe` в CI пока нет: бинарник получают в Конфигураторе командой сохранения расширения в файл, когда это нужно для дистрибутива.

### 4.3. Пользователь, от которого работает HTTP-сервис

HTTP-сервис исполняется **не** от имени живого бухгалтера, а от пользователя публикации (или пользователя HTTP-аутентификации — как настроено в `default.vrd`).

Создайте отдельного пользователя ИБ, например `мкпШлюз`:

1. **Администрирование → Пользователи**.
2. Новый пользователь, пароль только у администратора шлюза.
3. Роли:
   - **обязательно** `мкпДоступКоннектора` — Use HTTP-сервиса, чтение клиентов/словаря/ACL, запись журнала;
   - **плюс** роли (или набор прав), которые дают **чтение** тех справочников, документов и регистров, которые агент должен видеть. Роль коннектора **не** подменяет права на `Справочник.Контрагенты` и т.п.
4. Не давайте этому пользователю интерактивный запуск толстого клиента «на всякий случай», если политика безопасности это запрещает. Для HTTP-сервиса достаточно входа как пользователя ИБ.

Поле `ПользовательИБ` в справочнике клиентов интеграции в фазе 1 **хранится** для аудита и будущей связки с RLS; переключение сеанса на другого пользователя ещё не делается. Фактически данные читает пользователь публикации.

### 4.4. Клиент интеграции и токен

Токен в базе **не хранится**. Хранится SHA-256 (64 шестнадцатеричных символа, нижний регистр).

На машине администратора:

```bash
python3 -c "import hashlib,secrets; t=secrets.token_urlsafe(32); print('TOKEN='+t); print('HASH='+hashlib.sha256(t.encode()).hexdigest())"
```

Пример для демо-токена `dev-token` (только стенд, не прод):

```
TOKEN=dev-token
HASH=c91cbbedf8c712e8e2b7517ddeca8fe4fde839ebd8339e0b2001363002b37712
```

В 1С, предприятие (не конфигуратор):

1. Откройте справочник **1cmcp. Клиенты интеграции** (`мкпКлиентыИнтеграции`).
2. Создайте элемент, например «Claude Desktop / стенд».
3. Заполните:
   - **Наименование** — человекочитаемое имя приложения;
   - **Хеш токена** — 64 символа HASH, без пробелов;
   - **Скоупы** — строка `read` (через запятую можно `read,write`, но запись в Ф1 всё равно `501`; без `read` будет 403);
   - **Пользователь ИБ** — имя пользователя из п. 4.3, для журнала;
   - **Активен** — да.
4. Запишите. Сам TOKEN сохраните в секрет шлюза (`ONEC_TOKEN` / менеджер секретов), не в git и не в комментарий элемента.

Пока у клиента **нет ни одной строки** в `мкпПравилаДоступа`, ему разрешено читать любые объекты конфигурации **кроме** имён с префиксом `мкп`. Как только появляется хотя бы одно правило — действует белый список: видно только то, где **Разрешено = Да**.

### 4.5. Семантический словарь (чтобы агент находил «отгрузку»)

Без словаря поиск идёт по имени и синониму метаданных. На типовой ERP это часто `РеализацияТоваровУслуг`, а пользователь говорит «отгрузки». Заполните регистр **1cmcp. Семантический словарь**:

| Измерение | Пример |
|---|---|
| Вид объекта | `document` |
| Имя объекта | имя **как в конфигураторе**, например `РеализацияТоваровУслуг` |
| Имя поля | пусто — описание объекта; либо имя реквизита (`Контрагент`, `СуммаДокумента`) |

| Ресурс | Пример |
|---|---|
| Синонимы | `отгрузка, реализация, shipment` |
| Описание | что это за документ для агента |
| Примеры | `сколько отгрузок за август по контрагенту` |

Виды (`kind`) в API:

`catalog`, `document`, `information_register`, `accumulation_register`, `accounting_register`, `chart_of_accounts`, `chart_of_characteristic_types`, `enum`, `report`, `data_processor`, `constant`.

Для чтения в Ф1 осмысленны в первую очередь `catalog`, `document`, `information_register`, `accumulation_register`.

### 4.6. Публикация на веб-сервере

1. В Конфигураторе: **Администрирование → Публикация на веб-сервере**.
2. Каталог публикации и имя приложения (это `{ib}` в URL).
3. Включите **HTTP-сервисы**.
4. Укажите пользователя по умолчанию для сервисов — `мкпШлюз` (или эквивалент) **либо** настройте аутентификацию так, чтобы шлюз ходил с этим пользователем.
5. Опубликуйте. Перезапустите Apache/IIS, если мастер этого не сделал.

Базовый URL слоя A:

```
http(s)://{host}/{ib}/hs/mcp/v1/...
```

`mcp` — корневой URL HTTP-сервиса `мкпAPI`. Пример проверки с сервера шлюза (не из интернета):

```bash
curl -sS "http://1c-web/ut11/hs/mcp/v1/health"
```

Ожидание: HTTP 200 и JSON вида:

```json
{
  "status": "ok",
  "service": "1cmcp",
  "version": "0.3.0",
  "api": "v1",
  "time": "2026-09-09T18:00:00Z"
}
```

Если 404 — не опубликован HTTP-сервис, неверное имя ИБ или расширение не активно. Если 401/403 на health — смотрите аутентификацию веб-сервера (сам метод health токена коннектора не требует). Если 500 — смотрите журнал регистрации 1С, часто «безопасный режим» или нет прав на модуль.

Повторное использование сеансов уже задано в метаданных сервиса: `ReuseSessions = AutoUse`, `SessionMaxAge = 20` секунд. Не выключайте это в публикации без замера лицензий.

### 4.7. Сеть: 1С только для шлюза

- Публикация 1С слушает localhost / внутренний интерфейс / VPN.
- Файрвол: с хоста шлюза на порт Apache/IIS — да; из интернета на `/hs/` — нет.
- TLS между шлюзом и 1С желателен даже во внутренней сети.
- На проде планируйте mTLS; в Ф1 достаточно сети, недоступной агентам напрямую.

## 5. Шлюз, смотрящий в живую 1С

На машине шлюза (часто тот же VLAN, что веб-сервер 1С):

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e gateway
cp .env.example .env
```

Отредактируйте `.env`:

```
ONEC_BASE_URL=http://1c-web/ut11/hs/mcp
ONEC_TOKEN=<тот самый TOKEN, не хеш>
ONEC_TIMEOUT_SECONDS=30
GATEWAY_HOST=0.0.0.0
GATEWAY_PORT=8000
TENANT=default
META_CACHE_TTL_SECONDS=60
ONEC_PRESET=ut11
```

`ONEC_BASE_URL` — корень **включая** `/hs/mcp`, без `/v1`. Шлюз сам добавляет `/v1/...`.

`ONEC_PRESET` включает подсказки имён типовой: `ut11`, `ka2`, `erp2`, `bp30`, `auto`, `none`. На УТ поставьте `ut11`, на бухгалтерии — `bp30`. Зачем это нужно: [пресеты и навыки](skills.md).

Если веб-сервер 1С требует Basic/Windows-аутентификацию пользователя `мкпШлюз`, её нужно прокинуть отдельно (в Ф1 клиент шлюза шлёт только `Authorization: Bearer` токена коннектора). Практичный вариант стенда: публикация HTTP-сервисов с пользователем по умолчанию, без запроса пароля 1С у шлюза; изоляция — сетью.

Запуск:

```bash
python -m onecmcp serve --host 0.0.0.0 --port 8000
```

Проверка с той же машины:

```bash
curl -sS http://127.0.0.1:8000/ready
```

`/ready` ходит в `/v1/health` адаптера. `200` — контур живой. `503` с `code: adapter_unavailable` — шлюз не достучался до 1С (URL, сеть, публикация).

OpenAPI контракта:

```
http://127.0.0.1:8000/openapi.yaml
```

## 6. Подключить агента (MCP)

Шлюз REST (`serve`) и процесс MCP (`mcp`) — **разные** входы. Claude Desktop запускает MCP через stdio и сам ходит в слой A по `ONEC_BASE_URL`. Ему не обязателен `serve`, если агенту не нужен HTTP.

### 6.1. Claude Desktop

Файл конфигурации:

- macOS: `~/Library/Application Support/Claude/claude_desktop_config.json`
- Windows: `%APPDATA%\Claude\claude_desktop_config.json`

Вставьте сервер из [`docs/claude-desktop.mcp.json`](claude-desktop.mcp.json). **Замените** `command` на абсолютный путь к Python из venv (иначе Desktop может взять системный 3.11 и упасть):

```json
{
  "mcpServers": {
    "1cmcp": {
      "command": "/absolute/path/to/1cmcp/.venv/bin/python",
      "args": ["-m", "onecmcp", "mcp"],
      "env": {
        "ONEC_BASE_URL": "http://127.0.0.1:18080",
        "ONEC_TOKEN": "dev-token"
      }
    }
  }
}
```

Если пакет установлен в venv через `pip install -e gateway`, достаточно абсолютного `command` на `.venv/bin/python` и `args` как выше. `PYTHONPATH` не нужен.

Для живой 1С поставьте `ONEC_BASE_URL` как в `.env` шлюза и **боевой** токен.

Перезапустите Claude Desktop. В списке MCP-серверов должен появиться `1cmcp` с инструментами `health`, `meta_list`, `meta_search`, `meta_describe`, `data_list`, `data_get`.

### 6.2. Claude Code / Cursor

Тот же JSON в `.mcp.json` проекта или в настройках MCP IDE. Команда — `python -m onecmcp mcp` из окружения, где установлен `onecmcp`.

### 6.3. n8n, Dify, внутренний сервис без MCP

Они ходят **HTTP на шлюз** (`serve`), не в 1С:

```
GET http://gateway:8000/v1/meta/search?q=контрагент
Authorization: Bearer <token>
```

Шлюз проксирует `/v1/*` в адаптер и подставляет Bearer из `ONEC_TOKEN`, если клиент свой не прислал. На проде лучше, чтобы внешние клиенты не знали токен 1С, а получали отдельный контур (OAuth шлюза — фаза 4). В Ф1 на стенде один Bearer `dev-token` на мок/шлюз допустим.

## 7. Чек-лист «поставили правильно»

Отмечайте по порядку. Не переходите к агенту, пока красные пункты не зелёные.

- [ ] `python -m onecmcp --help` или `docker compose ps` показывает процессы
- [ ] `GET /v1/health` на адаптере (мок или `.../hs/mcp/v1/health`) → 200, `service=1cmcp`
- [ ] `GET /v1/meta` **без** токена → 401
- [ ] `GET /v1/meta` **с** `Authorization: Bearer …` → 200, в `items` нет имён на `мкп`
- [ ] `GET /v1/meta/search?q=…` находит объект из словаря или по синониму
- [ ] `GET /ready` шлюза → 200, внутри есть `adapter`
- [ ] в Claude Desktop видны шесть инструментов 1cmcp
- [ ] на живой 1С: расширение активно, публикация с HTTP-сервисами, пользователь с ролью `мкпДоступКоннектора` и правами чтения прикладных объектов
- [ ] 1С не открыта с интернета

Дальше — [как пользоваться](usage.md).

## 8. Лицензии 1С

Каждый сеанс HTTP-сервиса занимает клиентскую лицензию. У сервиса включено повторное использование сеансов (`AutoUse`, окно 20 с): пачка вызовов агента делит сеанс, простой отпускает лицензию.

Грубая оценка для пилота: **число одновременных сеансов шлюза ≈ число занятых лицензий**. Не направляйте чаты агентов напрямую в `/hs/mcp`. Отдельный пул лицензий для интеграции — требование пилота, не опция.

## 9. Обновление

1. Обновить git.
2. Расширение: снова **загрузить конфигурацию из файлов** в то же расширение `мкпКоннектор` и обновить конфигурацию БД. Данные справочника клиентов и регистров сохраняются, если не менялись имена объектов.
3. Шлюз: `pip install -e gateway` и перезапуск процесса/контейнера. Расширение у клиента трогать из‑за смены MCP **не** нужно — протокол живёт в шлюзе.

Откат: вернуть предыдущий `.cfe` / выгрузку и предыдущий образ шлюза независимо.

## 10. Типичные ошибки установки

| Симптом | Что проверить |
|---|---|
| `ModuleNotFoundError: onecmcp` | не активирован venv, либо `pip install -e gateway` не делали |
| мок стартует, шлюз 503 | другой порт; `ONEC_BASE_URL` без `/hs/mcp` для мока должен быть `http://127.0.0.1:18080` |
| health 200, meta 401 | не передан Bearer; на живой 1С хеш не совпал (другой токен, лишний перевод строки, хеш не SHA-256 hex) |
| meta 403 | в скоупах нет `read`; или уже заполнен ACL и объекта нет в белом списке |
| 404 на `/hs/mcp/v1/health` | публикация без HTTP-сервисов; неверное имя ИБ; расширение не активно |
| агент не видит «отгрузки» | нет строки в семантическом словаре; поиск идёт по имени метаданных |
| в выдаче нет нужного справочника | нет прав пользователя публикации на объект **или** сработало правило ACL |
| лицензии кончились у пользователей | слишком много сеансов HTTP; проверьте `AutoUse` и число воркеров шлюза |
