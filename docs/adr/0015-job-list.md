# ADR 0015. Список фоновых заданий текущего клиента

- Статус: принято
- Дата: 2026-09-10
- Фаза: Ф9

## Контекст

Ф2 дал `POST /v1/job` и `GET /v1/job/{id}`. После обрыва канала агент теряет `job_id` и не может найти свои задания. Регистр `мкпСостоянияЗаданий` уже хранил ресурс `Клиент`, но BSL его не заполнял: чужой UUID был читаем по прямому `GET`.

## Решение

1. Версия **0.10.0**.
2. **`GET /v1/job`** на том же пути, что POST. Скоуп `read`. Только задания текущего Bearer. Query: `limit` 1–200 (умолчание 50), `status` (точное значение). Новые сверху. Ответ: `content_kind: data`, `items[]` с `job_id`, `status`, `operation`, `at`. Поля `result` в списке нет — полный результат остаётся у `GET /v1/job/{id}`.
3. MCP-инструмент **`job_list`**.
4. `Поставить` пишет `Клиент`. `Получить(Ид, Клиент)` на чужое задание отвечает `404`.
5. Новый регистр не заводится.

OAuth и выгрузка чужих клиентов не входят в это решение.

## Последствия

- Агент восстанавливает свои `job_id` после обрыва без Конфигуратора.
- Клиент с одним `write` список не читает (`403`).
- Администратор 1С по-прежнему видит полный регистр; API наружу отдаёт только своего клиента.
