# ADR 0001. Трёхслойная архитектура

- Статус: принято
- Дата: 2026-09-09
- Фаза: Ф0

## Контекст

MCP, REST и OAuth меняются быстрее, чем выходят релизы 1С и чем клиент готов обновлять расширение. Держать протокольный слой внутри конфигурации значит тащить обновление `.cfe` на каждое движение спецификации.

## Решение

Три слоя с жёсткой границей ответственности.

| Слой | Где | Что делает | Чего не делает |
|---|---|---|---|
| A | Расширение `.cfe` в 1С | HTTP-сервис `/v1/*`, сериализация типов 1С, интроспекция, whitelist, журнал | JSON-RPC MCP, SSE, OAuth, OpenAPI для агентов |
| B | Python / FastAPI снаружи | MCP (stdio и streamable HTTP), OpenAPI 3.1, кэш метаданных, OAuth, лимиты, маршрутизация тенантов | Бизнес-логика 1С, прямое чтение СУБД |
| C | Агенты и приложения | Потребляют MCP или REST | Специальные доработки под 1С |

Между A и B — только HTTPS. Транспорт: mTLS или VPN. Прямая публикация HTTP-сервиса 1С в интернет запрещена регламентом.

Один шлюз обслуживает несколько информационных баз. Маршрутизация — по идентификатору тенанта (`X-Tenant` или сегмент пути шлюза). Контракт JSON между A и B один и тот же для всех баз.

## Последствия

- Обновление MCP — контейнер шлюза, расширение у клиента не трогается.
- Расширение остаётся тонким и реже ломает обновления типовых конфигураций.
- Без шлюза агент не получает MCP; REST к 1С остаётся внутренним контрактом слоя A.
