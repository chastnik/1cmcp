# ADR 0013. Журнал вызовов как API внутреннего контроля

- Статус: принято
- Дата: 2026-09-10
- Фаза: Ф7

## Контекст

Регистр `мкпЖурналВызовов` писался с Ф1, но читать его мог только консультант в 1С. План требовал аудит со ссылками на созданные объекты: агент и администратор должны видеть, что именно этот клиент интеграции вызывал, без доступа к чужим записям.

`/v1/health` и `/v1/diag` — живые пробы, не действия агента. Их в журнал не кладём.

## Решение

1. Версия **0.8.0**.
2. **`GET /v1/audit`** со скоупом `read`. Только записи текущего Bearer (`Клиент`). Query: `limit` 1–200 (умолчание 50), `since` (ISO-8601), `path` (префикс). Новые сверху. Ответ: `content_kind: data`, `items[]` с `id`, `method`, `path`, `status`, `duration_ms`, `at`, `created_refs`.
3. MCP-инструмент **`audit_list`** — та же проекция.
4. Ресурс регистра **`СсылкиJSON`**: JSON-массив ссылок объектов, затронутых вызовом (создание, изменение, проведение). Сбой журнала по-прежнему не ломает исходный ответ.
5. Текущий `GET /v1/audit` пишется в журнал **после** выборки: в своём ответе его ещё нет.

OAuth, внешний SIEM и выгрузка чужих клиентов не входят в это решение.

## Последствия

- Разбор инцидента агента — `GET /v1/audit` или `audit_list`, без Конфигуратора.
- Клиент с одним `write` журнал не читает (`403`).
- Администратор 1С по-прежнему видит полный регистр; API наружу отдаёт только своего клиента.
